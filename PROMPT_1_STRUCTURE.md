# FPL Predictor — PROJECT STRUCTURE PROMPT
(Paste this into VS Code / Claude Code / Cursor as your first instruction)

Build a project with exactly this folder and file layout. Do not
invent extra top-level folders. Every file listed has a specific,
single responsibility — do not merge responsibilities across files.

## Rules for whoever (human or AI) builds this

1. **One direction of dependency only**: `frontend` calls `backend/api`,
   `backend/api` calls `backend/src`, `backend/src` scripts never import
   from `api/`. If you find yourself importing api code into src/, stop —
   that's backwards.

2. **fetch_data.py, build_features.py, train_model.py, predict.py, and
   optimizer.py must stay independently runnable from the command line.**
   Each should work standalone with `python src/whatever.py`, producing a
   file on disk that the next script reads. This is intentional — it lets
   you debug the pipeline stage by stage without spinning up the API.

3. **Do not let the optimizer import the ML model, and do not let the
   model training code import PuLP.** These are two separate concerns
   (see architecture prompt) and mixing them into one file/class is the
   single most common mistake in FPL side projects — search GitHub and
   you'll see it constantly (model classes with squad-picking logic bolted
   on). Keep them separate even if it feels like more files.

4. **data/ is disposable.** Nothing in it should be hand-written or
   depended on existing — every file there must be regeneratable by
   running the scripts in order. Put it in .gitignore.

5. **Naming convention**: snake_case for all Python, PascalCase for React
   components, camelCase for TS variables/functions. Don't mix.

6. File size discipline: if any single .py or .tsx file exceeds ~250
   lines, that's a signal it's doing more than one job — split it.
